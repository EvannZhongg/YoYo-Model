# Agent 开发指导

本文件只规定实验决策和交付流程。项目结构、训练/评估命令、数据集约束和运行输出以根目录 `README.md` 及 `reports/` 为准，不在此重复。

## 工作约束

开始前检查 `git status`、当前分支和最近提交；保留用户已有改动。
所有代码、训练、评估和测试都在 `.venv` 中运行。新增依赖只安装到该环境，不修改系统 Python 或用户缓存。
先确认当前基线和评估协议，再开始实验。实验输出放 `runs/experiments/<run>/` 或 `tmp/`，不要把临时脚本扩散到正式模块。
每次候选实验都记录：代码/配置版本、数据 manifest、初始化权重、随机种子、主要参数、指标和运行时开销。训练运行的 `run_manifest.json` 是首选记录，不另造重复元数据。

## 优化取向

优先尝试模型结构、损失、输入、训练策略或数据表示的改进。
尽量减少用门控、多模型堆叠和场景路由修补单类问题；只有 A/B 有明确收益且成本可接受时才保留。
有效提升可以来自弱场景或全类场景；在其他关键指标不变时，单项指标的可靠提升也有价值。
默认要求推理吞吐不下降。若全局收益很大而只牺牲很小的速度、显存或参数量，必须量化代价并在报告中说明。
评估指标不合理时可以修改、删除或增加，但要先固定新协议，再重新评估基线和候选，不能混用不同口径的数字。
策略确认有效后，删除不必要的流程、组件和兼容分支，让默认路径只保留实际需要的模型。

## 候选判定

1. 在与基线相同的数据、输入尺寸、后处理和评估脚本下比较；同时看 pooled 指标、各弱场景/来源组和端到端 FPS/墙钟时间。
2. 检查局部回退。不能用平均数掩盖关键弱场景的严重下降；允许的回退必须写出范围、原因和收益交换。
3. 只有独立 test/连续集验证通过，且初始化权重没有污染评估来源时，候选才具备晋升资格。训练脚本和评估器中的 lineage/manifest 检查不得绕过。
4. 候选无效、收益很低、推理变慢或无法复现时，不作为候选保留：删除其专用代码、临时报告和无用流程，只保留必要的最小失败证据。
